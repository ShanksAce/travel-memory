# 口試說明
## 先用一句話介紹
「我把旅行前的規劃、旅行中的照片與心情、旅行後的地圖回憶整合在一起；照片整理使用 EXIF 與 GPS，資料不足時讓使用者修正。」

## 照片上傳後放在哪？
照片原始 bytes 放在 R2，D1 只存檔名、分類日期、城市、GPS 與 object key。讀照片要先查照片所屬旅行是不是目前使用者的。

## 為什麼不把照片直接存進資料庫？
一般列表需要的是日期與城市，不需要每次載入大圖片。分開儲存可讓結構化查詢與檔案讀取各自處理，但要注意兩個服務之間没有共同交易，刪除失敗需要補償機制。

## 為什麼是 SQL？
旅行與相片、日記、行程之間有明確的一對多關係。外鍵能表達歸屬，索引改善依帳號／旅行查詢，級聯刪除避免孤立子紀錄。

## 如何避免 SQL injection？
使用 prepared statements 綁定值。動態表名僅能來自後端固定對照表，欄位由 Zod schema 解析後產生，不能由使用者自由指定 SQL。

## EXIF 是什麼？一定有嗎？
EXIF 是影像內的拍攝中繼資料，例如日期、相機資訊、GPS。社群轉存、截圖或關閉定位的照片常沒有 GPS。系統不假裝知道位置，會保留旅行預設或標示待確認。

## GPS 怎麼變成城市？
這版用約 50 個離線城市中心點。計算 GPS 到每個城市的大圓距離，最近且小於 50 公里才建議城市。它是範圍有限的近似分類，不是完整 reverse geocoding。

## 為什麼不直接用 AI？
這個問題先利用照片已具備的資料就能解決部分整理工作，方法較易解釋、成本低、結果可驗證。AI 景點辨識需要資料、評估集與錯誤處理，這版沒有實作。

## 登入怎麼做？
線上由 Sites 的登入入口處理，平台轉送穩定的使用者 ID；後端用該 ID 驗證每次存取。本機是僅限開發環境的模擬身分，不可直接當成正式登入服務。換到其他主機，需要另接可信登入及驗證機制，不能相信瀏覽器自行送的身分 header。

## 天數怎麼計算？
倒數使用日曆日期差；旅行天數用已到來日期的集合，避免重疊旅行重複計算。已到訪城市以打卡日期判定，不把未來計画算成既有成就。

## 怎麼證明功能真的有作用？
除了操作畫面，也透過 API 建立紀錄後重新查詢，確認修改／刪除結果；上傳照片後讀回原始 bytes 比較；用合成 JPEG 的已知 EXIF 日期與 GPS 驗證分類。

## 測試能證明沒有漏洞嗎？
不能。測試驗證特定情境，尚未完成多帳號雲端端到端驗證、負載與滲透測試。正式上線需加入更多驗證、監測、配額、備份與故障補償。

## 最大技術限制？
照片 GPS 不完整、離線城市覆盖有限，以及相片數量很大時缺少縮圖和分頁。這些限制都有具體改善方向，可作為下一阶段研究。
